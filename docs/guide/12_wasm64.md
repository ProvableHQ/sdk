The SDK ships two WebAssembly builds of the same Rust sources and snarkVM
version. The default build targets wasm32, where linear memory is capped at 4
GiB. The wasm64 build targets `wasm64-unknown-unknown`, addresses memory with
64-bit pointers and sets an 8 GiB maximum. Both builds are threaded and keep the
Rayon pool.

# When the wasm64 build applies

The 4 GiB cap bounds what one SDK instance can hold at once. A developer reaches
it with large or concurrent workloads. Cases that apply:

- Local proving of functions whose proving keys, circuits and witnesses do not
  fit side by side in 4 GiB.
- Many proofs generated concurrently in one instance, where each in-flight proof
  holds its own keys and execution trace.
- Record scanning over a large set of ciphertexts, with decryption, when the
  working set stays resident.
- Many cryptographic operations in flight at once, such as batched signing,
  hashing or key synthesis across a worker pool.

The wasm64 build is slower per operation. Measured on Node.js 24 and an Apple
M2, every benchmarked operation took 9 to 21 percent longer than on wasm32, and
proving took 13 to 18 percent longer. The build is worth that cost only for
workloads that do not fit in 4 GiB.

# Installing and importing

```bash
npm install @provablehq/sdk @provablehq/wasm64
```

```js
import {
    Account,
    ProgramManager,
    initThreadPool,
} from "@provablehq/sdk/wasm64/mainnet.js";

await initThreadPool(6); // Pool size depends on the application and the host.
```

The testnet import is `@provablehq/sdk/wasm64/testnet.js`. CommonJS uses the
same paths with `require()`. Loading a network at runtime is available at
`@provablehq/sdk/wasm64/dynamic.js`.

`@provablehq/wasm64` is an optional peer dependency of the SDK, versioned in
lockstep with `@provablehq/wasm`. The wasm32 entry points do not need it, and
installing the SDK alone does not pull it in. The low-level bindings and workers
are `@provablehq/wasm64/{mainnet,testnet}.js` and
`@provablehq/wasm64/{mainnet,testnet}/worker.js`.

# Selecting a variant at runtime

The wasm64 entry points throw on runtimes without 64-bit shared WebAssembly
memory. The default imports are unchanged, and there is no automatic fallback.
An application that also targets runtimes without wasm64 support selects the
variant once, before initializing the SDK:

```js
let wasm64 = false;
try {
    new WebAssembly.Memory({
        initial: 0n,
        maximum: 1n,
        shared: true,
        address: "i64",
    });
    wasm64 = true;
} catch {}
const sdk = wasm64
    ? await import("@provablehq/sdk/wasm64/mainnet.js")
    : await import("@provablehq/sdk/mainnet.js");
```

The check covers the memory model only. It does not confirm that the context can
start Workers.

The choice MUST be made in one place. Objects created by one variant MUST NOT be
passed to the other, and the bindings and workers of a variant MUST be used
together. Loading both variants in one process creates two wasm instances with
separate memories and thread pools.

# Memory

The wasm64 build sets an 8 GiB linear-memory maximum. Shared memory reserves
address space for the full maximum when it is created. The reservation is
virtual address space rather than physical memory, so it rules out 32-bit hosts
but does not guarantee that the host has enough memory for the workload.

# Runtime support

"SDK" means that the threaded build initializes and `initThreadPool` works. Both
variants need Workers and shared memory. Browsers also need cross-origin
isolation, as for the wasm32 threaded build.

Verified rows were tested with this build: browsers in a cross-origin-isolated
module worker, Node.js with the installed packages. Each test starts two Rayon
workers, signs a message and runs a program offline. Expected rows follow from
the engine's wasm64 support and are not yet tested. The Node.js rows are
asserted on every pull request by the `runtime compat` jobs in
`.github/workflows/sdk.yml`, which install the packed packages on each Node.js
line and, where the table says No, check that the wasm64 entry points throw the
documented error.

# Building from source

`yarn build:all` builds both WebAssembly variants and the SDK. The toolchain,
the two Binaryen versions, the dependency patches and the lockfile handling are
described in the
[WASM build instructions](https://github.com/ProvableHQ/sdk/blob/mainnet/wasm/README.md#wasm64-build).
